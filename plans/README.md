## How to contribute

Every plan issue (#5–#16) starts with a **"Who's on it & how to help"** box: status, owner, whether it's up for grabs, what it's waiting on, and open questions.

- **Pick something up:** comment "taking this" on the issue and assign yourself. Issues stay unassigned until someone actually starts.
- **Use a coding agent:** pull `main`, then tell your agent: *"Read `plans/NNN-name.md` and follow it step by step. Run every verification command, only change files listed under Scope, stop and tell me on any STOP condition, don't push."* Review the result and open a PR that says `Closes #N`.
- **Answer questions:** reply on the issue by question number.
- For plans that need careful judgment (006, 007, 009 renderers, 010), use the strongest model your agent offers.

## Architecture in one picture

```
 ┌──────────── apps/web (Vite) ────────────┐   ┌──────── apps/mobile (Expo) ────────┐
 │ screens, filters UI, chat bubble        │   │ screens, filters UI, chat bubble   │
 │ @transit/maps/web  (MapLibre GL JS)     │   │ @transit/maps/native (MapLibre RN) │
 └───────────────┬─────────────────────────┘   └───────────────┬────────────────────┘
                 │  @transit/shared: zod schemas + types + API client + TripDraft reducer
                 ▼                                              ▼
 ┌──────────────────────────── apps/server (Fastify) ─────────────────────────────┐
 │ routes/      HTTP endpoints, validation with shared zod schemas                │
 │ planning/    rank + constraint check (pure, tested)                            │
 │ providers/   RouteProvider interface → fixture | transit (OTP/Google) | flight │
 │ agent/       ADK LlmAgent (Gemini) → tools call planning/providers             │
 │ store/       node:sqlite — users, profiles, saved itineraries, watches         │
 │ watch/       interval job: refresh realtime → recompute leave-by               │
 └─────────────────────────────────────────────────────────────────────────────────┘
```

**Design rules every plan follows** (from the design threads):

- **One preference system, two inputs.** The filters UI and the agent both produce the same
  `TripDraft`. The agent never invents a route. It edits the draft and calls tools, and the
  server does the searching, constraint checks, and ranking.
- **Requirements vs preferences.** Hard constraints (`arriveBy`, `maxBudgetUsd`, …) exclude
  options. Preferences (comfort vs cost, risk tolerance) only rank them. An option that
  breaks a requirement is shown only as an explained "almost works" item.
- **Freshness is part of the data.** Every itinerary and leg says where its times came from
  (`scheduled` / `realtime` / `estimated`) and when it was fetched. The UI must never present a
  scheduled bus time as if it were live.
- **The map renders, the app decides.** Map components take `itineraries`,
  `selectedItineraryId`, and `onRouteSelect`, and never fetch or save anything.
- **Booking is deferred.** Show booking links at most. Agent-initiated purchases need
  app-owned confirmation and idempotency (ADK tool confirmation is experimental in TS).

### D10 in detail: where flight prices come from

[Clovis](https://github.com/Cattn/clovis) is Cattn's flights project. It talks to Google Flights' internal endpoints with plain `fetch` (no browser), throttles requests, and already supports **several origin airports in one search** (`from=BOS,PVD,MHT`), which is exactly what "is it cheaper to fly from another airport" needs.

| Option | How | Good | Bad |
|---|---|---|---|
| **A. Port Clovis's client** *(recommended)* | Copy its `src/utils` (`tfs.ts` URL builder, `shopping.ts`, `parser.ts`, `token.ts`, `format.ts`) into `apps/server/src/flights/clovis/`, wrap it as a `ClovisFareProvider` behind plan 014's `FlightFareProvider` interface | Real Google Flights prices, free, no API key, one server process, Cattn knows the code | Unofficial: Google can change the page or show a captcha at any time, and it isn't sanctioned by Google's terms. Fine for a local demo, not for a product. Times come as local strings and durations as `"5h 30m"`, so they need converting to ISO times with offsets. |
| B. Run Clovis as a service | Start Clovis next to our server and call its HTTP API | No code copied; Clovis improvements arrive for free | Two processes to run (and Clovis uses Bun); same unofficial-source risk as A |
| C. Duffel | Official flight API; test mode is free | Sanctioned, structured data, can book later | Account and key needed; test mode may return sample airlines rather than real prices (verify); real use is paid |
| D. SerpApi (Google Flights) | Paid service that returns Google Flights results as JSON | Simple, maintained by someone else | Small free quota; comparing ~5 origins × 3 destinations uses it up fast |
| E. Sample fares only | Plan 014's `FixtureFareProvider` | Never breaks; perfect for a demo script | Not real prices |

**"Have the agent check flights itself"** works as a layer on top of any source, not as a source by itself. Letting the model read prices off web pages is slow and can't be checked, and it breaks the rule that the agent never invents a route. Instead, give the agent a `search_flights` tool backed by A–E, and let it *decide which searches to run*: try other airports, shift dates ±2 days, or for Europe, try several landing cities and compare the train onward. That's where the agent adds value (plan 006 tool + plan 011 step 7).

**Decided:** keep sample fares for testing; copy Clovis in and adapt it to return *all* flights, not just the cheapest (plan 019). Original recommendation: keep sample fares (014) for development and the demo fallback; build A as plan 011 step 6 with caching and the existing throttle; add the agent's `search_flights` tool on top. Revisit C if booking ever matters.

## Backlog (not planned yet, deliberately)

- **Booking.** Needs app-owned confirmation and idempotency keys before any agent tool can spend money.
- **Europe / Eurail "cheapest place to land" search.** It needs a multi-destination fare search plus a rail pass model.
- **Probabilistic transfer risk ("how evil a transfer can I do").** v1 uses deterministic rules
  (buffer minutes vs. a realtime/scheduled flag). Showing an actual probability requires
  historical delay data we don't have. Don't display made-up percentages.
- **Tracking where your car/bike is left between trips** (from the map thread). The `TripDraft`
  in 002 has `vehicles` fields so this can be added without reshaping.
- **Streaming agent responses (D5-B): planned**, the owner wants it after plan 006's request/response version (see 006 maintenance notes). **Push notifications (D7-C).**

## Findings considered and rejected

- *Add `fastify-type-provider-zod`*: rejected for now. Manual `schema.safeParse` in each route
  is three lines, avoids zod-version coupling with ADK, and is easier for agents to follow.
- *Put React hooks in `@transit/shared`*: still rejected. Shared stays framework-free so the server
  can import it. Hooks get their own package instead (`@transit/client-react`, plan 015).
- *More CI work now*: rejected. The existing `ci.yml` already runs lint, typecheck, build, and
  smoke. Plan 001 adds unit tests to `npm test`, which CI already runs.
