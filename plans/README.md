## How to give feedback

1. **Decisions (D1–D12 below)** each have a recommended default. Reply with `D4: B` or
   `D4: B, because …`. Plans that depend on a decision say "Blocked by Dn"; until you answer, executors use
   the recommended default.
2. **Each plan ends with "Open questions for review".** These are smaller design choices with a
   proposed answer already written into the plan. Comment by plan and question number, e.g.
   `002-Q3: drop rideshare`.
3. **The data contract (plan 002) is the review that matters most.** The server, agent, map
   and both UIs all depend on it. Adding a field later is cheap. Renaming or reshaping one after
   the UI and map teams build against it is not.

## Architecture in one picture

```
 ┌──────────── apps/web (Vite) ────────────┐   ┌──────── apps/mobile (Expo) ────────┐
 │ screens, filters UI, chat bubble        │   │ screens, filters UI, chat bubble   │
 │ @transit/maps/web  (MapLibre GL JS)     │   │ @transit/maps/native (MapLibre RN) │
 └───────────────┬─────────────────────────┘   └───────────────┬────────────────────┘
                 │  @transit/shared: zod schemas + types + API client + TripDraft reducer
                 ▼                                              ▼
 ┌──────────────────────────── apps/server (Fastify) ─────────────────────────────┐
 │ routes/      HTTP endpoints, validation with shared zod schemas                │
 │ planning/    rank + constraint check (pure, tested)                            │
 │ providers/   RouteProvider interface → fixture | transit (OTP/Google) | flight │
 │ agent/       ADK LlmAgent (Gemini) → tools call planning/providers             │
 │ store/       node:sqlite — users, profiles, saved itineraries, watches         │
 │ watch/       interval job: refresh realtime → recompute leave-by               │
 └─────────────────────────────────────────────────────────────────────────────────┘
```

**Design rules every plan follows** (from the design threads):

- **One preference system, two inputs.** The filters UI and the agent both produce the same
  `TripDraft`. The agent never invents a route. It edits the draft and calls tools, and the
  server does the searching, constraint checks, and ranking.
- **Requirements vs preferences.** Hard constraints (`arriveBy`, `maxBudgetUsd`, …) exclude
  options. Preferences (comfort vs cost, risk tolerance) only rank them. An option that
  breaks a requirement is shown only as an explained "almost works" item.
- **Freshness is part of the data.** Every itinerary and leg says where its times came from
  (`scheduled` / `realtime` / `estimated`) and when it was fetched. The UI must never present a
  scheduled bus time as if it were live.
- **The map renders, the app decides.** Map components take `itineraries`,
  `selectedItineraryId`, and `onRouteSelect`, and never fetch or save anything.
- **Booking is deferred.** Show booking links at most. Agent-initiated purchases need
  app-owned confirmation and idempotency (ADK tool confirmation is experimental in TS).

## Backlog (not planned yet, deliberately)

- **Booking.** Needs app-owned confirmation and idempotency keys before any agent tool can spend money.
- **Europe / Eurail "cheapest place to land" search.** It needs a multi-destination fare search plus a rail pass model.
- **Probabilistic transfer risk ("how evil a transfer can I do").** v1 uses deterministic rules
  (buffer minutes vs. a realtime/scheduled flag). Showing an actual probability requires
  historical delay data we don't have. Don't display made-up percentages.
- **Tracking where your car/bike is left between trips** (from the map thread). The `TripDraft`
  in 002 has `vehicles` fields so this can be added without reshaping.
- **Streaming agent responses (D5-B), push notifications (D7-C).**

## Findings considered and rejected

- *Add `fastify-type-provider-zod`*: rejected for now. Manual `schema.safeParse` in each route
  is three lines, avoids zod-version coupling with ADK, and is easier for agents to follow.
- *Put React hooks in `@transit/shared`*: rejected. Shared stays framework-free so the server
  can import it. The UI team owns hooks in each app (see 004 maintenance notes).
- *More CI work now*: rejected. The existing `ci.yml` already runs lint, typecheck, build, and
  smoke. Plan 001 adds unit tests to `npm test`, which CI already runs.
